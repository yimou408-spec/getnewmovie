## 1. 开发目标与启动顺序

首版交付：居家观影场景下，用户自然语言输入需求，系统理解和必要追问、筛选候选、自动查询豆瓣及其他独立评价来源，整理低剧透口碑对照，一次性返回最多3部；支持比较、反馈、已看记录和明确确认的长期偏好。

采用单 Agent＋LangGraph 受控工作流。首要顺序：运行环境与现有基线 → 豆瓣及第二来源验证 → 身份/契约/规则 → 证据处理 → Agent闭环 → 界面、记忆及整体验收。

豆瓣必须自动获取。评分、搜索结果外链、人工录入或用户粘贴不能单独替代自动取得评价证据的验收。单片可以缺证降级，整个豆瓣通路始终不可用则不能宣称首版核心完成。

## 3. 分阶段开发计划

A/B/C沿用现有三人分工：A前端，B服务与数据，C推荐与Agent。以下是三人持续投入下的阶段工作日估算，不是个人工时，也不是承诺完成日期；包含联调、测试和修正。外部账号审核、数据使用条件确认及人员等待另计。

| 阶段 | 建议工期 | 主要任务 | 可交付结果及进入下一阶段的条件 |
|---|---|---|---|
| M0 环境与基线 | 0.5–1天 | 统一Python/Node，建立.venv，安装现有锁定依赖，跑S0检查，确认网络与配置注入 | 其他成员可复现启动；现有检查通过，或明确修复和记录现有失败 |
| M1 数据与模型可行性 | 2–4天验证窗口 | 验证自动豆瓣、影片库、第二评价来源、搜索与目标LLM；记录身份匹配、证据范围、耗时和成本 | 豆瓣自动评价证据与独立第二来源有可复核案例；来源适用条件清楚；真实模型能稳定输出结构化条件 |
| M2 契约、影片身份与筛选 | 2–3天 | 固定请求/结果/澄清/降级契约；影片ID映射；硬过滤、已看排除、排序去重、0–3部不足处理 | 固定数据下关键硬条件通过；同名翻拍不混淆；前后端共享样例与Schema |
| M3 证据工程 | 3–4天 | 将可行来源封装成适配器；规范片段、作者、时间、内容粒度；去重、独立来源分组、缓存、缺证状态 | 能从真实自动取得的材料输出影片级证据包；只有评分或外链不冒充口碑对照 |
| M4 Agent闭环 | 3–4天 | 结构化理解与追问、需求到工具路由、受限补查、观点提取、分歧整理、低剧透解释、输出校验 | 单Agent工作流可端到端运行；达到预算/时限停止；本次结果一次性返回，失败明确降级 |
| M5 Web与交互联调 | 2–3天 | 自然语言入口、澄清、结果卡、出处、比较、反馈、加载/空态/错误/降级状态 | 用户能实际输入并完成选片；处理中不提前显示未完成推荐；结果能打开对应来源 |
| M6 基础记忆与状态管理 | 2–3天 | SQLite已看/偏好/反馈；开关、确认、修改删除；会话与长期区分；缓存和检查点关联处理 | 跨会话可使用明确记忆；临时意愿不永久保存；记忆关闭仍可推荐；数据隔离与删除验证通过 |
| M7 评估、演示与交付 | 2–3天 | 固定任务集、真实冒烟、端到端回归、基线对比、成本/时延报告、启动与故障说明 | 自动豆瓣和真实多源演示可复现；硬规则与引用检查通过；已知限制、运行配置和评估结果完整 |

顺序估算约17–25个团队工作日，待M1结束重估。A可从M2起按契约并行做M5，B/C可在领域骨架可用后并行推进适配器和工作流，不能简单把各阶段天数除以三。

M1的2–4天是验证和形成决策的窗口，不保证豆瓣问题在此期间解决。若未通过，继续推进来源申请/适配验证；界面、离线规则与契约可独立推进，但不能以这些替代核心功能验收。任何降低豆瓣要求的方案都需要重新讨论产品范围。

## 5. M1必须准备并产出的验证材料

### 5.1 影片与评价样本

- [ ] 人工核对现有30条影片查询种子中的身份，保留同名、翻拍、冷门、中文和外语电影差异。
- [ ] 初次低额度探测先用3部；扩展目标建议至少10部用于真实评价链路验证，报告分母和失败案例，不只展示成功片。
- [ ] 评价样本覆盖有丰富评价、评价稀少、观点分歧、只有摘录、来源失败和潜在剧透等情况。
- [ ] 每条材料记录影片ID、平台、原作者/发布者、原始链接、采集时间、正文/摘录/评分、独立来源组、可支持的陈述和使用范围。
- [ ] 片名/年份/外部ID匹配需人工参考答案；自动搜索第一条结果不能直接作为真值。

### 5.2 自动豆瓣与多源验证的通过条件

- [ ] 系统自动匹配到正确豆瓣影片；验证同名与翻拍，不把别的电影评价拼入结果。
- [ ] 自动取得可支持具体口碑判断的豆瓣评价材料，明确正文或摘录粒度；记录字段与覆盖缺口。
- [ ] 对同一影片取得另一独立评价来源；转载同一篇材料只算一组证据。
- [ ] 能还原从观点到出处的映射；链接和原文范围可复核。
- [ ] 在不同时间做有限重复验证，测量成功率、更新时间、耗时与调用消耗；不以一次成功宣称长期稳定。
- [ ] 空结果、访问限制、超时、字段变化分别返回受控状态，不把所有失败都说成“没有评价”。
- [ ] 来源适用条件与访问方式有记录；尚未确认的事项不能记为已通过。

现有TMDB探测器只覆盖影片信息、关键词、别名与观看渠道索引，尚未验证评价获取。模型探测器只测固定句子的结构化解析。需要补充豆瓣及多源证据探测与测试，不能把已有探测通过等同于新目标通过。

### 5.3 模型验证

- [ ] 当前选定协议能被适配器调用；若不是/chat/completions协议，需要对应适配器。
- [ ] 能正确解析否定、时长、临时要求与长期偏好，不凭空填写未知条件。
- [ ] 结构化输出失败、超时、限流有受限修复和回退。
- [ ] 原文提取与总结不混淆来源观点和模型推断；生成引用可对应实际材料。
- [ ] 记录模型名/版本、提示词版本、Token用量、费用和耗时；不把供应商选择建立在未测的价格或效果承诺上。

- [ ] 保持默认测试离线；真实冒烟显式启用且有限额，不把外部网络放入每次提交的稳定测试。
- [ ] 使用TDD验证有实际业务意义的条件、来源映射、降级、预算、临时偏好和跨用户隔离。
- [ ] 扩充现有30条合成任务，移除首版暂缓项的必做要求，加入自动豆瓣、多源独立性与一次性返回场景。
- [ ] 冻结开发集与独立评估集；人工标注长尾相关性、引用支持与剧透风险，不能以模型自评替代真值。
- [ ] 准备普通LLM直接推荐、同工具但无记忆、规则筛选等基线；保持候选池、数据权限与任务条件可比。
- [ ] 准备测试用户和匿名记录表；愿看率、选定耗时、信任和观后满意度有实际数据后再报告。
- [ ] CI更新契约、后端和前端检查；提供启动、备份恢复、配置、故障说明及演示脚本。
- [ ] 对外展示前确认托管位置、持久化目录、HTTPS、认证、预算告警和日志处理；本机演示可后置这些部署工作。

## 8. 分工与可以并行的工作

| 角色 | 最先执行 | 后续主责 | 共同评审 |
|---|---|---|---|
| A 前端 | 基于共享样例画清一次性结果、澄清、证据不足状态 | Web、比较、反馈、偏好管理、端到端 | 契约是否能表达界面实际状态 |
| B 服务与数据 | 环境、豆瓣/影片/第二来源验证与配置 | 适配器、API、SQLite、缓存、外部请求计数、CI | 来源身份、出处、数据存储与故障 |
| C 推荐与Agent | 样本/参考答案、模型小实验、硬规则验收 | 过滤排序、LangGraph、观点整理、低剧透和评估 | 证据是否支持结论、记忆语义与成本 |

B/C共同完成M1，A可同步准备交互状态。数据获取未通过时，可以做接口、合成Mock和规则，但必须持续清楚标注数据模式。

每个任务用“用户故事 → 验收例 → 失败测试 → 最小实现 → 回归与PR”推进。各自分支开发，PR说明变更行为、验证结果及剩余限制。API字段修改同步更新Schema、共享样例和界面。
