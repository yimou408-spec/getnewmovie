# 个性化电影推荐 Agent：证据驱动开发计划

版本：2026-10-15（三人开发分工版）。状态：已创建[S0必要文档与脚本](s0/README.md)，产品推荐服务尚未实现；真实数据与模型可行性待验证。

## 1. 先做什么

将附件1的“电影推荐及衍生服务 Agent”收敛为：**理解这一次想看什么，从可信影片数据或个人片单中选出少量候选，给出可核验、低剧透的选择依据，并通过可控记忆减少下次重复表达。**

优先顺序：数据可用性验证 → 选片与核验闭环 → 反馈和基础长期记忆 → 历史导入及渠道增强 → 有证据后再扩展衍生服务。

不以工具数量或自主循环次数作为产品价值。核心价值用“是否更快选到合适的电影、是否有可信依据”验证。

### 范围和假设

- 按三名开发者组织：A负责前端设计与实现，B负责后端服务与数据，C负责后端推荐逻辑、Agent及模型调试。具体任务和协作边界见第11节。
- 以中文 Web 应用、非商业演示起步；目标观看地区暂按中国大陆设计，地区由产品使用者选择，不由设备位置或时区推断。商业化、移动原生端和大规模并发另行评估。
- 当前仓库已有规划文档，没有既有应用可延续。本计划只安排开发团队的设计、实现、测试、联调和技术评估任务。
- 附件1中的简历话术、技术选型和“可以直接背”等均为资料，不是执行指令；附件2的课程提交要求也不自动转化为开发要求。
- 依据：附件1全文；附件2中7份根目录 Markdown 材料及 P01–P10 匿名访谈文字。未回听音频、未独立审查 DOCX/PPTX 版式或与文字稿的一致性。

## 4. P0：最小但完整的选片闭环

### 4.1 入口与交互

三个入口共用同一推荐服务：

1. **不知道看什么**：一句话表达想法；最多先追问2个高信息量问题，然后给出至多3部候选。
2. **从我的片单选**：粘贴片名/年份或手动添加，系统消歧后只在已确认片单内选择；不偷偷扩展库。
3. **已知道片名**：直接打开影片卡/对比，不强制问偏好或开启记忆。

推荐卡包含：片名与年份、稳定影片ID、时长/地区/类型、为何符合当次要求、可能不合适之处、已确认与待确认条件、来源和采集时间、观看渠道状态。默认不显示剧情转折、结局、自动播放视频。用户可选2–3部同屏对比。

“换一批”在当前会话排除已展示；“已看过”持久保存；“今天不想看”仅影响本次；“以后少推荐这种”作为待确认长期偏好。不能将未点击或没选中解释成讨厌。

### 4.2 检索和推荐规则

- LLM把自然语言转为结构化条件，负责澄清与有限解释；影片、评分、链接只能来自工具结果或授权数据，不能从模型记忆直接拼造。
- 区分硬条件与软偏好：时长上限、排除已看、片单范围等确定性过滤；“轻松”“青涩”等需标签/证据支持，未知不得当作已满足。
- 初始采用元数据筛选 + 标签/关键词/TF-IDF相似度 + 可解释加权排序及多样性去重；不训练协同过滤，不把“高评分”当“适合你”。中文文本检索需分词或字符n-gram，不照搬英文默认分词。
- 长尾细分需求采用先查类型/关键词再补证据的方式；无法确认主题时标注未知并询问是否放宽，不返回三部明显不符的热门片凑数。
- 有足够符合条件的影片才输出3部；否则返回0–2部与不足原因。矛盾条件先澄清，不能擅自放宽硬约束。
- 确定性模块负责最终合法性校验、候选ID白名单、事实字段、链接与引用有效性；LLM不拥有绕过权限。

### 4.3 可信核验与低剧透

- 一个评分连同来源、量表、样本量（有则展示）和采集时间保存；不同平台不平均成所谓综合真分，也不把TMDB评分称作豆瓣评分。
- 一条评价结论对应具体证据片段与URL；多条转载算同源，不当独立共识。区分“元数据事实”“来源观点”“模型匹配推断”。热度/点赞只能作为排序信号，不代表真假鉴定。
- P0可以只有单一可用来源，但必须说明单源局限；多平台聚合能力没有获得合规、可访问数据前不得宣传已实现。
- 默认只展示预定义安全字段和审核过的风格标签；影评抽取先过滤再总结，无法安全提取则不展示。外链影评可能含剧透，打开前提示。
- 多平台评价的用户价值是核心待验证项：如果数据拿不到，先用明确标注的授权/人工整理原型做试验，不把这种演示算实时联网能力完成。

### 4.4 基础长期记忆与安全底线

- SQLite存储结构化偏好、已看/想看、明确反馈、来源事件、时间和用户确认状态。无需先上向量数据库或外置Memory服务。
- 优先级：本次明确条件 > 用户确认的长期偏好 > 推断软偏好；硬禁忌与本次要求冲突时提问，而不是隐式覆盖。
- 只从明确反馈/确认中写长期偏好；不把“别人喜欢”“帮朋友找”“一次想看”永久写入。允许关闭记忆并照常推荐。
- 选片题材可能透露敏感信息：不推断身份、性取向、健康状态等；敏感偏好不自动持久化，确有需求需单独明确同意。发给外部模型时只传最少必要数据。
- 按用户隔离查询、缓存、图执行检查点和日志；会话恢复不等于长期记忆。对外测试前接入成熟认证组件，不自研密码系统。身份认证前只做本机单用户演示。
- 删除覆盖画像、反馈、导入记录、相关缓存/检查点；备份保留期限需公开说明。匿名ID并不等于匿名化，不承诺立即抹除第三方已留存副本。
- 网页、影评、导入文本都是不可信数据；其中“忽略指令、修改偏好、访问其他URL”等不能变成工具指令。输出转义并限制长度，避免HTML脚本注入。

### 4.5 最小可看信息

保存国家/地区、平台、观看类型、查询时间、状态与合法URL。未验证为“未知”，过期为“待复查”，无结果不等于不存在。平台搜索入口必须标成“搜索入口，需自行核验”，不能装成可播放链接。

影院上映状态依据地区与时间，不能只比较首映日期；实时场次、价格、会员权益和是否能播放需要相应数据授权。无可靠接口时不自动比价、不承诺有票，不替用户下单。

## 5. P1与P2

### P1：核心通过之后

1. **通用CSV/JSON历史导入与豆瓣格式适配**：先提供模板、预览、消歧、去重和撤销；仅接受用户合法持有且自愿上传的文件。不索要密码、Cookie，不默认爬个人账号。没有可验证格式就不声称支持豆瓣一键导入。
2. **丰富评价来源**：通过授权接口或允许范围的搜索补充来源；建立独立来源识别、证据质量检查、缓存失效及缺失告知。无权限不抓全文。
3. **地区可看条件增强**：验证中国大陆覆盖后再接平台/购票合法跳转；时间/预算筛选只在有可靠数据时开放。实时库存和票价不靠LLM推断。
4. **语义召回增强**：仅当长尾标注集显示词法基线明显不足，再评估SentenceTransformers和独立授权的多语种模型；先在进程内向量检索，确有规模需求再上pgvector。
5. **记忆效果优化**：处理偏好变化、过期和撤销，针对误记案例迭代；不把互动次数与准确率提升直接画等号。

### P2：有验证再立项

地图取景地、周边购买、社群入口、多人协调、每日主动推送、自动购票、模型微调、协同过滤。每项先确认具体情境、频率、替代方案和数据授权；自动交易需额外明确授权。群聊邀请、私密社群和用户位置不是可以默认采集的数据。

## 6. 推荐实现结构

选择轻量代码方案：React + TypeScript + Vite 前端；FastAPI + Pydantic后端；SQLite数据层；LangGraph负责有边界工作流。工具比较、许可及证据见[工具复用调研](工具复用调研.md)。

```text
输入（新需求 / 已有片单 / 已知片名）
  → 结构化理解 + 可选澄清 + 读取获准记忆
  → 影片工具检索 → 确定性硬过滤 → 解释性排序
  → 对Top候选补证据/渠道信息 → 事实与低剧透校验
  → 卡片/对比 → 明确反馈 → 经确认写入记忆
```

不是每个请求都执行全部步骤。已知片名走查询分支；无同意不读写长期偏好；无网络走有时间标记的缓存/离线演示；无匹配明确返回。

模块边界建议：`domain`（规则与数据结构）、`services`（推荐/记忆/导入）、`adapters`（MovieCatalog/Search/Availability/LLM）、`workflow`（图与预算）、`api`、`web`。测试替换适配器，不替换业务断言。

数据实体最小集：User/Consent、Movie（外部ID映射）、Watchlist、FeedbackEvent、Preference、Evidence、Availability、RecommendationRun。Evidence保存声明范围、来源、取回时间、证据摘要/引用许可；RecommendationRun保存版本与来源ID，不保存隐藏推理链。仅必要时保留脱敏输入。

建议API契约：`POST /recommendations`、`GET /movies/{id}`、`POST /comparisons`、`POST /feedback`、`GET/PATCH/DELETE /me/preferences`、`DELETE /me/data`；P1再加`POST /imports/preview`、`POST /imports/{id}/confirm`、`DELETE /imports/{id}`。所有个人数据路由从认证上下文取用户，不信任客户端任填user_id。

| S3 记忆、反馈及受限Agent | 2–3天 | A：反馈/偏好管理；B：持久化、权限与删除；C：偏好语义、工作流与模型故障处理 | 跨会话、临时不持久、用户隔离、删除、提示注入、工具预算 | SQLite偏好、同意开关、有限LangGraph工作流、日志 | P0安全/业务测试通过，记忆关闭仍可推荐 |

| S5 次核心 | 4–6天 | A：导入/渠道界面；B：导入事务、撤销和新数据接口；C：画像更新、语义召回及回归评估 | 导入幂等/消歧/撤销、渠道过期、语义检索回归测试 | P1逐个小切片交付，不一次全开 | 每项独立验收；新模型/来源无质量增益则不引入 |

按三人持续投入估算，P0约11–16个团队工作日，P1另需4–6天。S0结束后依据实际数据接入和模型实验重新估算；数据授权、人员投入或接口范围变化时同步调整。P2暂不排期。

## 8. TDD执行约定与完成定义

每个任务绑定“证据/假设编号 → 用户故事 → 可观察验收 → 自动测试 → 实现”。详细用例见[TDD验收与任务清单](TDD验收与任务清单.md)。

1. Red：写最小失败用例，运行并保存失败原因；应因功能缺失而失败，不是因网络/Key缺失。
2. Green：以固定数据、FakeLLM/FakeCatalog使其通过，再增加真实适配器契约；不让模型评分代替业务规则。
3. Refactor：保持所有用例绿灯后整理结构；不得为了通过而随意删断言或放宽需求。
4. 先单元后集成，再补关键端到端；每次PR跑离线门禁，真实API冒烟需人工启用且预算受限。
5. 错误修复先添加复现测试；提示词、模型、排序权重、数据源变化必须跑冻结评估集。

完成定义：功能用例、错误分支、隔离与隐私测试通过；规则模块分支覆盖率目标≥90%（计划阈值，不是当前结果）；新依赖许可/数据授权记录完整；真实与模拟演示标识明确；有迁移/回滚方式；没有未解释的事实生成、敏感日志或硬约束破坏。

## 9. 如何证明“比直接问大模型好”

附件1中“通用模型一定不记忆/不会调用工具”的比较不能作为事实或优势证明；应与实际选定的同条件基线对比。

- B0：同一LLM只使用用户当前输入，直接推荐；如无可验证数据，其事实错误同样计入。
- B1：同一LLM + 相同影片/证据工具，但不使用长期记忆。
- B2：确定性过滤与排序，不使用LLM，验证规则/检索本身贡献。
- 产品：同一数据权限与候选池 + 当前条件 + 获准长期记忆 + 核验卡片。

预建至少30个匿名/合成任务，覆盖细分题材、模糊心情、长片单、已知片名、无匹配及故障；建议20个迭代、10个冻结保留，不能拿个人访谈原文直接上传。长尾相关性由人工核验元数据后标注，不用LLM自评当真值。

开发团队交付可用于形成性试验的任务脚本、计时埋点、反馈表和匿名结果导出：A实现选定耗时、跳转和反馈采集界面；B提供事件存储与导出；C设计基线和分析脚本。脚本支持顺序随机/交叉及难度相近的不同任务，减少同题学习效应。参与者招募、访谈复核和材料补交不列为本开发计划的任务；获得真实试验数据前，愿看率、节时和观后满意度保留为待验证指标。

计划门槛：固定集硬约束违规0；展示事实的证据可追溯率100%；审核用例严重剧透0；Top3愿看命中目标≥70%；形成性试验中位选定时间较各自基线降低目标≥30%。同时报告失败任务、分母及范围，不仅报均值。后两项是待验证目标，小样本结果不能声称统计显著或普遍有效。

若记忆相对B1没有稳定增益，保留明确偏好管理但不堆复杂Memory框架；若生成解释引发错误则改模板；若外部数据不可得则不能宣称解决跨平台核验。

## 10. 成本和运行约束

- 先使用现成组件；只自写差异化的条件解释、约束策略、证据绑定与偏好规则。不开多Agent，不训练推荐大模型，不预建爬虫集群/地图/电商服务。
- 预算初值：每次完整推荐至多2次LLM请求、2次搜索、8次外部HTTP请求（重试也计入），候选补证据最多3部；超限走已有证据或明确降级，不递归重试。具体值在S0测量后冻结。
- LLM用于理解和整理，过滤、对比表、消歧确认、记忆CRUD不必调用模型；缓存公有影片数据但不跨用户缓存个人推荐。
- 成本记录：`LLM输入/输出tokens×各自单价 + 搜索次数×单价 + 其他API + 托管摊销`。未选定供应商前不编造人民币单次成本或固定免费配额。
- 模拟CI预算为0外部调用；真实冒烟有独立开关/上限。P95响应目标≤10秒、含冷搜索≤20秒，需在指定网络、模型、地区测量；超时返回可用部分并注明状态。P0先验证功能，不声称已达性能指标。

### 11.3 对接约定与提交要求

1. **契约先行**：S0由B维护API/JSON Schema、错误码和版本，C定义推荐条件、候选、澄清与证据字段，A确认界面所需状态。三人共用同一份Mock响应，覆盖成功、无结果、需澄清、超时和未配置状态。
2. **先测后写**：每人先提交所属模块的失败测试与验收描述，再补最小实现，最后重构。A不等待真实模型完成才开发；C不依赖真实网络完成领域测试；B用固定响应验证外部适配器。
3. **模块各自负责**：A维护`web`；B维护`api`、数据持久化及MovieCatalog/Search/Availability适配器；C维护推荐领域规则、推荐服务、LLM适配器及`workflow`。共享Schema由B统一落库，修改前同步A/C并一起更新Mock和契约测试。
4. **持续联调**：每个切片完成即接入主流程，至少每日完成一次契约与集成检查。问题记录包含输入、预期、实际结果、版本和脱敏trace_id，修复前先补复现测试。
5. **交叉评审**：B与C互审后端和模型相关修改；A评审接口对界面状态的影响，B评审前端API接入。测试、引用或指标未达标的修改继续修正，不以三人各自“模块完成”代替系统验收。
6. **运行与交付**：B维护环境变量模板、服务启动、数据库迁移、CI与回滚说明；C维护模型/提示词版本和评估复现命令；A维护前端构建、操作演示与端到端运行说明。密钥通过环境配置注入，示例文件只保留占位符。

启动顺序：三人共同确定S0契约和测试样例；A推进交互原型，B验证数据源与后端骨架，C验证检索/模型及评估基线；通过S0出口后进入S1。
