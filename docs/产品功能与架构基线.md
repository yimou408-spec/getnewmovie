## 1. 项目定义

面向已经有居家观影意图、尚未确定片名的人，通过自然语言理解当下需求，筛选少量候选，自动获取豆瓣及其他独立来源的评价，提供低剧透、可追溯的口碑对照，帮助用户选定电影。

核心交付是“有依据地完成选片”：既需要找到候选，也需要帮助用户判断候选。最终选择由用户完成。

### 已确认的设计树

```text
居家观影 → 有依据地完成选片
├─ 入口：自然语言找片为主，候选比较作为接续对话
├─ 输出：最多3部候选，完成本次检索与核验后一次性展示
├─ 依据：跨平台口碑对照
│  ├─ 豆瓣必须包含，且必须自动获取
│  ├─ 需要其他独立评价来源
│  └─ 单部影片证据不足可以降级，必须说明缺口
├─ 个性化：已看记录＋明确确认的长期偏好
└─ 架构：单 Agent＋LangGraph 受控工作流
```

## 2. 与第一阶段研究材料的关系

课程第一阶段是用户研究与痛点定义，并未承诺具体产品功能。本轮是在该研究基础上进行产品设计，不能把设计选择写成已经验证的研究结论。

- 核心研究问题：跨平台过滤和核验有效信息存在负担。
- 关联问题：当下偏好难以收窄为候选，判断质量与避免剧透之间存在取舍。
- 样本限制：主题覆盖人数不能直接当总体发生率；长期记忆提升推荐效果、跨平台汇总节省时间等仍需验证。
- 对照案例说明：已有明确片名、导演或系列偏好的人，可能无需复杂推荐流程。

研究来源位于仓库上一级的“第一阶段提交材料”，尤其是 `07_Top3核心痛点.docx`、`08_ProblemStatement.docx`、`10_第一阶段研究报告.docx`。

## 3. 首版功能范围

| 功能 | 用户行为 | 系统责任 | 可观察结果 |
|---|---|---|---|
| 需求理解与澄清 | 输入心情、题材、时间、排除项等 | 区分硬条件与软偏好；关键条件不明或矛盾时追问 | 用户能理解并修正本次条件 |
| 候选检索与筛选 | 请求推荐、补充条件或换一批 | 检索真实影片，过滤已看与不满足硬条件的结果 | 最多3部；不足时可返回0–2部，说明原因 |
| 自动豆瓣查询 | 无需另行提供评价材料 | 匹配正确影片，自动取得可用信息与评价证据 | 保存原始链接、采集时间、内容范围和查询状态 |
| 跨来源口碑对照 | 查看推荐依据 | 查询其他独立评价来源，识别重复转载，整理共识与分歧 | 每条口碑判断可追溯，覆盖不足明确显示 |
| 低剧透解释与比较 | 询问“为什么适合”“这两部怎么选” | 结合当次需求解释取舍，避免主动披露转折和结局 | 显示匹配点、不适合之处及证据缺口 |
| 连续反馈调整 | 表达“太压抑”“已看过”“换一批” | 根据反馈更新本次条件或已看记录，重新执行必要步骤 | 后续结果遵守新增条件 |
| 基础长期记忆 | 明确要求记住偏好，管理已有记录 | 保存已看影片和明确确认的偏好，支持查看、修改、删除 | 下次减少重复表达；临时心情不自动持久化 |

低剧透是默认内容策略，不承诺任何自由文本均绝对没有剧透。外部链接内容与系统展示摘要的风险需要分别处理。

首版暂缓：个人片单批量导入、自动学习隐性兴趣、每日推送、多人协调、实时票价和场次、自动购票、全平台播放能力、地图、周边和社群。当前优先解决选片与口碑判断。

## 4. 一次完整的使用流程

示例输入仅用于说明交互，不代表真实影片或评价数据：

> 今晚自己看，两个小时以内，想看悬疑，但别太压抑。

1. 提取本次条件，读取获准的已看记录与明确偏好。
2. 若有影响结果的歧义或冲突，先向用户澄清；澄清是独立交互，不需要等待全部检索完成。
3. 检索候选，对时长、已看等条件执行代码过滤。
4. 对候选自动查询豆瓣与其他评价来源，核对影片身份、内容范围及来源独立性。
5. 根据证据缺口决定是否继续检索；达到时间或调用上限后停止补查。
6. 形成低剧透的推荐与比较，检查事实字段、引用和证据状态。
7. 一次性返回本次结果。等待期间可显示“处理中”状态，不提前展示未完成的候选或局部口碑判断。
8. 用户选定、比较或补充条件；只重新执行受影响的步骤，缓存必须保留来源和采集时间。

推荐卡片应包含：影片身份与基本信息、符合哪些要求、可能不适合之处、豆瓣与其他来源各自的信息、口碑共识或分歧、可打开的出处、采集时间和缺失说明。

## 5. 如何定义“口碑核验”

必须区分三类内容：

| 内容类型 | 例子 | 处理方式 |
|---|---|---|
| 可核对事实 | 片名、年份、时长、某平台评分及其量表 | 对应到数据来源；冲突时保留差异或标为待确认 |
| 来源观点 | 某位作者认为节奏慢、部分评论认为氛围压抑 | 归因到具体材料，说明样本范围；不能冒充所有观众共识 |
| 匹配推断 | 因用户今晚想放松，所以某片优先级较低 | 明确这是基于需求和证据的推荐判断 |

核验包括影片身份核对、来源追踪、重复转载识别和观点对照。不默认具备评论真伪鉴定、刷分识别或全网口碑覆盖能力。

评分分别展示，不把不同平台量表直接平均成“真实综合分”。两个网址、两个域名不必然代表两个独立观点源；基础元数据与播放渠道也不算独立评价来源。

搜索摘录、正文、评分必须区分。只读到摘录时，只能支持摘录范围内的陈述；没有读到全文时不能宣称已经完成全文分析。

## 6. 豆瓣硬要求与单片降级

这两项要求同时成立：

- 产品层面：必须有真实可工作的豆瓣自动信息获取通路，并能展示豆瓣与其他独立来源的评价对照。只有评分和外链不足以证明已完成评价内容分析。
- 单部影片层面：即使某次只有一个来源或评价不足，也可以推荐，但需要明确标为证据不足，不得显示为已完成多源核验。

用户粘贴、人工预录、合成数据可以用于调试，不能替代豆瓣自动获取的验收。整个豆瓣通路不可用时，仍可返回明确降级的结果，但核心豆瓣功能不能算完成。

自动获取不要求每次重新抓取全部内容。可使用自动采集的缓存，但必须保留采集时间；具体有效期、刷新规则和覆盖范围需验证后制定。

截至本轮核查，豆瓣接入尚未验证：官方电影页直接访问遇到安全校验，开发者入口未能读取；可检索的历史页面索引不等于已接入当前评价。既不能据此承诺接口可用，也不能据此断言不存在可用接口。

## 7. 已选 Agent 架构

采用单 Agent＋LangGraph 受控工作流。单 Agent 表示由一个助手维护目标和对话状态；多个处理节点不等于多个独立 Agent。

```text
理解需求 → 必要澄清 → 读取获准偏好 → 召回与硬过滤
    → 豆瓣及其他评价检索 → 身份/重复/覆盖检查
    → 按需补查（有上限） → 低剧透综合 → 输出校验
    → 一次性展示 → 比较/反馈 → 必要时更新明确记忆
```

| Agent/LLM负责 | 代码与规则负责 |
|---|---|
| 理解自然语言、识别需要澄清的问题 | 条件结构校验、硬过滤、已看排除 |
| 在允许来源内组织检索词、建议补查 | 豆瓣必查、来源约束、超时与调用预算 |
| 从取得的材料中提取观点、整理分歧 | 保存出处与内容范围、检查引用可对应性 |
| 根据需求解释取舍 | 不允许绕过硬条件或生成不存在的事实字段 |
| 提出可能需要记住的偏好 | 用户确认后的持久化、读取隔离、修改与删除 |

来源检索可以并发，用户界面仍按一次性返回策略展示。工作流控制失败与停止条件，不能无限自主检索。

## 8. 建议编码模块

以下是后续拆分建议，具体接口仍需数据验证后细化：

```text
web/          对话、推荐卡、对比、反馈、偏好管理
api/          请求、会话、结果与错误接口
workflow/     图状态、路由、补查与停止条件
domain/       影片、需求、证据、偏好及硬规则
services/     推荐、口碑对照、比较、记忆服务
adapters/     影片库、豆瓣、其他评价/搜索、模型、存储
tests/        规则、适配器、流程和端到端验收
```

最小工具边界：影片检索、豆瓣证据获取、其他来源检索/读取、偏好存储。工具返回结构化内容与状态，模型负责解释；不让模型直接生成评分、来源网址或数据库写入结果。

仓库既有 FastAPI/Pydantic 契约和 S0 样例可继续利用。React、SQLite等沿用已有开发建议。模型服务已确定DeepSeek Flash，接入方案与验证见[限期开发实施计划](限期开发实施计划_20261029.md)；搜索服务、第二评价源、部署方式和预算尚待落实。

## 9. 接下来先验证什么

优先验证自动豆瓣通路及第二来源，不先扩建完整界面。验证应形成可复核记录：

1. 能否自动找到并确认正确影片，覆盖同名、翻拍等情形。
2. 能取得哪些豆瓣字段及评价内容；接口、访问与使用条件是否支持项目用途。
3. 第二来源是否提供独立观点，而非转载豆瓣材料。
4. 每条判断能否对应来源、内容范围与采集时间。
5. 公开数据与评价缺失、访问失败、超时分别如何返回。
6. 测量响应耗时与调用成本后，再确定候选召回量、补查次数、缓存有效期和超时预算。

数据验证通过后，依次实现：确定性筛选骨架 → 自动证据获取 → 对话理解和综合 → 比较与反馈 → 基础长期记忆 → 整体验收。

## 10. 首版验收基线

- 真实用户输入能触发需求理解、筛选、自动查证和完整结果返回。
- 展示真实的豆瓣自动获取及另一独立来源对照案例，不能用Mock代替。
- 硬条件不能被推荐解释绕过；无匹配允许返回空结果。
- 影片事实、平台评分和引用均能对应实际取得的数据；评价结论受证据范围约束。
- 单片证据不足如实降级；豆瓣系统性不可用不得算豆瓣功能验收通过。
- 结果一次性展示；超时后可以返回完整的降级结果，而非无限等待。
- “今天不想看”只影响本次；明确长期偏好可管理，已看记录影响后续筛选。
- 冻结示例任务并与普通模型直接推荐作对比；愿看率、决策耗时和信任改善均为待测结果，不能预先宣称有效。

## 11. 与旧开发计划的差异

- 豆瓣从“非首版实时依赖”改为“必须自动获取的核心来源”。
- 丰富评价来源与跨来源口碑对照从增强方向上移为首版核心。
- 单源仅作为具体影片的降级情形，不能替代整个产品的多源验收。
- 交互采用本次查询完成后一次性返回，停止或超时条件必须明确。
- 自然语言找片为主入口，比较作为后续对话；自有片单导入暂缓。
- 检索次数、模型调用次数和响应时间沿用旧计划的数值仅可视为待测初值，不能直接当已确认承诺。
