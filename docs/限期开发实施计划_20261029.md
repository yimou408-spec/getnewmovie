### 数据可行性与边界

- 已核对 [IMDb 非商业数据集](https://data.imdb.com/non-commercial-datasets/)及[官方使用说明](https://help.imdb.com/article/imdb/general-information/can-i-use-imdb-data-in-my-software/G5JTRESSHJBBHTGX)：免费集合含 `title.basics`、`title.akas`、`title.ratings` 等，**没有用户影评正文**；官方说明禁止依此许可对网站使用 robots/screen scraping。把目标换成 IMDb 不等于已有免费爬取通路。
- [官方 GraphQL API](https://data.imdb.com/documentation/api-documentation/)和[批量产品](https://data.imdb.com/documentation/bulk-data-documentation/)通过 AWS Data Exchange 提供。需先核对选定产品是否确实包含需要的逐篇影评、摘录/存储/展示/模型处理权限与费用；不假定注册 IMDb/IMDbPro、API试用或“User Review Summaries”产品自动提供原始用户影评。供应商汇总观点不能冒充多个原作者的逐字评价。
- 本轮不申请付费订阅、不启用未经核对的数据通路，也不增加一个填上就假装接通的 `IMDB_API_KEY` 开关。当前没有生产 IMDb 采集适配器，响应为 `IMDb/not_configured`，`reviews` 能力保持实际配置状态。

2026-11-02复核：官方[User Review Summaries字段说明](https://data.imdb.com/documentation/bulk-data-documentation/data-dictionary/user-review-summaries/)明确为AI汇总，包含`titleId/userSummaryText/themes/publishedAt`，不提供逐篇原文、作者或评论ID，不能替代本轮引用。官方[API申请](https://data.imdb.com/documentation/api-documentation/getting-access/)需AWS账户及订阅审批，现有公开元数据产品不能证明含影评正文。I01目前是**外部数据产品及授权卡点**，不是等待填写通用API Key；不为解决正文问题购买未确认产品。

账号持有人可通过[官方联系表单](https://help.imdb.com/contact/developer/)或`imdb-licensing@imdb.com`询问以下内容；本轮未代发联系或申请订阅：

1. 是否提供按`tt` ID取得**逐篇用户影评原文**的产品；请给产品名称、文档和脱敏字段样例，区分AI summaries。
2. 样例是否含评论ID、作者署名、原始URL、发表/更新时间和剧透标记。

4. 试用是否覆盖10片（含近90天影片、每片至少2篇）、调用限额/更新频率及总费用。

取得书面依据和字段样例后再继续I03/I05；若不提供逐篇影评，需要用户重新决定来源或缩小正文功能范围。真实人工引用/低剧透抽审、C08与真人试用继续等待真实材料，不用合成材料代签。

## 1. 交付目标与工期约束

### 1.1 最终必须能演示的业务

用户表达居家观影需求 → 必要追问 → 结合偏好检索与筛选 → 自动查询豆瓣及其他独立评价来源 → 整理口碑共识与分歧 → 一次性展示最多3部 → 用户比较、反馈或选定。

必须包括：

1. 自然语言理解，区分硬条件和软偏好。
2. 稳定影片身份、去重、已看排除、最多3部与无匹配处理。
3. 真实自动取得豆瓣评价证据及另一独立评价来源，保留可复核出处。
4. 低剧透解释、评分来源分开、口碑差异与不适合之处。
5. 比较、换一批、已看、今天不想看等连续反馈。
6. 明确确认的长期偏好与已看记录；支持开关、查看、修改、删除。
7. 单Agent＋LangGraph受控工作流；补查、重试与时间均有上限。
8. 本次推荐结束后一次性返回；单片证据不足明确降级。

豆瓣整条通路不可用时，不能将用户粘贴、人工预录、其他平台评分或搜索链接当成自动豆瓣功能完成。演示可以使用自动采集缓存，但须展示采集时间，并能复现至少一条自动更新路径。

### 1.2 为截止日期控制的范围

首版按本机启动的Web Demo设计。沿用主仓库React/TypeScript/Vite和FastAPI/Pydantic，增加SQLite与LangGraph，复用真实目录、规则、类型、测试和探测脚本。主模型使用DeepSeek Flash。

暂缓：个人片单批量导入、三套独立入口、自动推断隐性兴趣、推荐模型训练、独立向量数据库、复杂Memory服务、主动推送、多人协调、实时票价和场次、自动购票、全平台播放、地图、周边和社群。

“暂缓”指不增加这些能力的开发范围；主仓库已有零输入、点选、已知片名、本次片单和比较保持兼容，不为了本轮聚焦而删除。自然语言成为新增主路径，已有点选作为辅助；不扩建长期片单和导入系统。

若要求公网多人试用，需要另落实托管、HTTPS和成熟认证；这些不在当前本机演示基准工时内。代码仍从开始保留服务端用户上下文，并测试身份隔离，避免后续大改。

## 7. DeepSeek Flash接入方案

用户已选DeepSeek Flash。2026-10-20读取的官方说明使用模型ID `deepseek-flash`，OpenAI兼容基础URL为 `https://api.deepseek.com`；该别名当时对应DeepSeek-V4.1-Flash-1017。模型别名可能更新，实验记录须保存响应中的实际model值，不能假设可以通过别名锁死权重版本。[官方接入说明](https://api-docs.deepseek.com/)

当前项目变量约定：

```text
LLM_BASE_URL=https://api.deepseek.com
LLM_MODEL=deepseek-flash
LLM_API_KEY=由账号持有人在本机设置
```

现有探测器会追加 `/chat/completions`，因此不要把完整端点再次填入基础URL。官方示例使用的DEEPSEEK_API_KEY与仓库现有LLM_API_KEY不是同一变量名；首版统一通过设置层映射，不能仅设置前者就假定旧脚本会读取。

本节以下是设计选择，须以C01测试确认：

- 首先沿用HTTPX＋统一LLM适配器，结构化内容经Pydantic校验。
- 每轮主路径预计一次理解、一次综合；允许全局最多一次格式修复。只有必要步骤调用模型，过滤、记忆CRUD、静态对比表不调用。
- 不依赖尚未验证的strict JSON Schema、原生函数调用或联网能力。图可根据校验后的结构化动作在白名单工具中路由。
- 现有探测器max_tokens=150只适合极小样例，不能直接作为综合阶段限制。明确记录finish_reason、空content、截断、推理/输出用量和修复原因后确定各阶段上限。
- 思考模式及其参数单独验证，优先满足延时和结构稳定性；不假设默认值，不展示或存储不必要的内部推理内容。
- 官方文档提示有Search/Fetch能力，但本次未验证该能力能读取豆瓣；可作为C02候选，与独立搜索/页面读取服务比较后决定，不能因模型已选择就把网络问题视为解决。
- 费用按实际账单或验证当日官方单价计算，单独记录模型、搜索、页面读取费用；本轮未取得可据以承诺的价格表，不编造每次费用。

## 9. 工具、数据和接口的最小规格

### 9.1 工具结果与状态

MovieCatalog、DoubanEvidence、OtherReviewEvidence、PreferenceStore是核心边界。搜索是发现工具，不是独立评价源。所有工具返回结构化结果及错误，不让模型拼造URL、评分或数据库写入结果。

来源状态至少区分：ok、no_results、not_configured、access_limited、timeout、parse_error；公开缓存另记录fresh/stale与采集时间。具体枚举在Y02统一，前端不解析自然语言错误来判断逻辑。

每条证据最少包含：evidence_id、movie_id、平台与来源名称、原作者/发布者、原始URL、来源内容ID（如有）、采集时间、正文/摘录/评分粒度、独立来源组、支持的陈述、剧透等级及使用范围依据。

平台评分保留value、scale、vote_count（有则展示）和evidence_id。评分、影片简介和评论不能拆算成三个独立来源。

### 9.2 推荐与比较

- 召回量、重排量和证据补充量分开，最终最多3部；初值可尝试召回20–30部、规则收窄到5–8部、只对最终候选补查，按实际延时调整。
- 时长、已看、明确排除等硬条件由代码执行；未知字段不能假定合格。含糊情绪先作为需证据支持的软条件，明确禁忌需要确认与证据处理。
- 同名影片按稳定ID/年份/别名/导演等消歧，不能把第一条搜索命中直接作为真值。
- 保留现有itunes:和tmdb:等命名空间，单独维护豆瓣/外部ID映射；不强制替换现有前端已经选择的ID。同片跨源归并依人工参考和确定性映射，翻拍不合并。
- 新文字与已点选条件矛盾时澄清，不静默覆盖；无文字点选可直接复用规则分支。现有备注“不参与匹配”的提示在自然语言能力真实接入后更新，不能只改文案。
- 解释分为metadata_fact、source_opinion、matching_inference；每个可引用观点绑定同片证据。
- 口碑对照只描述取得的样本；两个独立样本观点相近不等于全网共识，保留分歧与不确定性。
- 默认低剧透，拒绝不安全的引用预览；不能安全生成时回到可靠字段和明确缺口。
- 比较复用本次证据，不为静态字段重复请求模型；用户追加新问题时才考虑补查。

### 9.3 会话和长期数据

建议实体：本地用户/同意、Session、Movie及外部ID映射、Evidence、RecommendationRun、FeedbackEvent、Seen、Preference。公共影片证据缓存和个人排序/反馈分别存储。

首版可采用请求级LangGraph执行，澄清所需上下文由服务端Session保存；不必额外部署图持久化服务。若启用检查点，删除和用户隔离必须覆盖检查点。

用户说“已看过”写入已看记录；“今天不想看”只改本次；长期偏好仅在明确确认后保存。偏好修改要使个人派生缓存失效；帮朋友找电影不能误写本人喜好。

### 9.4 API清单（Y02冻结具体类型）

| 方法/路径 | 业务 | 主要字段或行为 | 主责 |
|---|---|---|---|
| POST /sessions | 创建服务端会话 | session_id由服务端生成；身份来自服务端上下文 | Y |
| POST /recommendations | 输入/澄清/换批后的推荐 | query、session_id、constraints、memory_enabled；返回最终候选、证据、覆盖和警告 | Y接口/C图 |
| GET /movies、GET /movies/{id} | 查询/消歧与详情 | 实体不确定需要确认；不强迫偏好问卷 | Y |
| POST /comparisons | 比较2–3部 | movie_ids及本次运行引用；复用证据，不平均评分 | Y接口/P展示/C解释 |
| POST /feedback | 已看/临时排除/偏好提议/确认/撤销 | event_id幂等，session_id、movie_id、类型及确认状态 | Y/C |
| GET/PATCH/DELETE /me/preferences | 偏好和开关 | 版本、确认状态、修改删除语义 | Y接口/C语义/P界面 |
| GET /me/seen | 已看列表 | 支持查看与相应反馈撤销 | Y/P |
| DELETE /me/data | 清理个人数据 | 关联删除范围明确，后续空画像开始 | Y/C/P |

推荐状态沿用ready、empty、needs_clarification、degraded；澄清是一次独立交互，不违反“结果一次性返回”。故障导致最终degraded时可以0–3部，但必须说明原因。缺少核心配置可返回受控服务错误，不偷偷切换合成数据。

| 单次推荐总时限 | 60秒绝对时限 | 超时返回最终降级/受控错误；前端等待上限应更长，如75秒 |
| LLM调用 | 主路径理解＋综合；全局至多1次格式修复，总计至多3次 | 各阶段输出预算、截断和用量，不各自无限重试 |
| 搜索/HTTP预算 | 先测≤2次搜索、≤18次外部HTTP，失败/分页/重试计数 | 是否覆盖3部×2源的真实链路；不够需显式调整 |
| 外部并发 | 最多3路 | 限流、源访问条件与取消处理 |
| 元数据缓存 | 7天起步 | 缺失/新片变化，显示更新时间 |
| 评价缓存 | 24小时起步 | 原始材料使用条件、更新与覆盖；不是实时全量口碑 |
| 评分缓存 | 6小时起步 | 投票变化和来源可用性；过期标stale |
| 每次补查 | 最多一个补查轮次 | 必须有证据缺口和剩余预算，补查后无论成功失败结束 |

适配器按剩余总时限设置自己的请求超时；图步骤、重试和并发不能绕过同一账本。网络失败和模型失败均要有最终状态。缓存命中不将旧采集时间改成当前时间。

尚待账号持有人给出探索总预算和每日限额。未给额度前，只完成离线实现与配置检查，不默认开展无限收费实验；首次少量探测应有显式上限和用量记录。

## 11. 测试与评估安排

### 11.1 日常检查

- 默认离线：领域单元、HTTPX MockTransport外部契约、FastAPI集成、临时SQLite、组件和Playwright测试。
- 主仓库已有连接真实Apple上游的Playwright及frontend CI。保留该真实验收用途，另以显式live job/开关与稳定离线检查分离；不能直接将现有联网测试称为离线，也不能用注入合成影片冒充真实上游成功。
- 每个切片先有可观察失败和验收，再写最小实现；修复先保留复现例。
- 真实冒烟显式启用、受预算约束，结果与离线CI分开；缺Key不能使稳定CI随机失败。
- 变更类型时重新导出Schema，样例和UI同步；既有S0门禁继续检查，不以新产品代码覆盖旧工具损坏。
- 只有文档更改不必安装模型或编造业务测试结果。本计划创建时未运行产品测试。

### 11.2 样本和冻结集

| 材料 | 计划规模 | 用途 | 主责 |
|---|---:|---|---|
| 首轮联网影片 | 3部 | 最低额度验证身份和自动内容 | Y/C |
| 数据验证影片 | 10部 | 覆盖同名/翻拍、常见/冷门、中外、少评价、冲突/缺证 | Y准备，P/C复核 |
| 离线任务 | 30条，20开发＋10冻结 | 规则与失败路径；修订现有合成任务以符合首版范围 | C |
| 真实质量子集 | 每个比较方案建议最多10条，受预算约束 | 人工审引用支持、相关性、低剧透与证据范围 | C主分析，P/Y分担审核 |
| 形成性试用 | 建议3–5位志愿者 | 输入到选定耗时、选择理由、信任和体验问题 | P组织，C出脚本 |

预算不足或未招到用户的项目标pending，不伪造结果。直接模型、相同工具无记忆、规则筛选等比较要保持任务和数据条件可比；不将模型自评当真值，不把小样本节时结论推广到所有观众。

### 11.3 本计划建议的交付门槛

- 固定测试中硬条件违规、错影片引用和虚构评分/URL均为0。
- 数据验证10部全部报告分母和状态；建议至少8部身份明确且正确匹配，至少5部自动取得豆瓣与另一独立评价源的可引用材料。达不到时如实记录并评估交付风险，不删除失败样本提高比例。
- 至少一个真实演示能从用户输入自动取得豆瓣并完成多源对照；自动采集缓存和新采集路径均能追踪。
- 默认摘要与引用预览的严重剧透审核样例无泄露；同时保留“不承诺自由文本绝对零剧透”的范围说明。
- 0/1/2/3部、需澄清、模型失败、豆瓣失败、第二源失败、全网不可用、总时限和预算耗尽均有确定终点。
- 已看持久、临时意愿不持久、确认偏好跨会话、关闭记忆、改删及测试身份隔离通过。
- 一次性返回通过端到端检查；结果不会因旧请求晚到覆盖新请求。
- 全新环境能按文档启动并复现固定演示；报告版本、模型别名/响应model、提示词和采集时间。
- 用户愿看率、节时率和真实使用价值以实际数据报告，不设未经验证的“高精准已完成”结论。

## 13. 每日工作节奏与完成定义

建议每天4h实施拆成两个2h块；另外2h依次做模块回归、交叉评审和联调。10分钟状态同步包含在联调时间内，避免另加会议侵占计划。每个任务详情、前置和主审见台账。

任务完成必须同时具备：业务验收例、实际实现、适用检查结果、主审意见已处理、接口/样例/文档已同步、证据或PR链接。只有“代码写完”“发出了PR”“我电脑能跑”均不足以独立判完成。

每日更新至少包含：任务ID、实际投入、已完成验收、前置阻塞、次日安排、剩余风险。任务状态统一not_started / in_progress / blocked / review / done；缓冲任务先为conditional。这里的blocked是项目台账字段，不是对话目标状态工具。
